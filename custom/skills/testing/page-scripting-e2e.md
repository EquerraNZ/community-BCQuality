# BC Page Scripting E2E

Build a durable, repeatable browser-level test layer for a Business Central
extension using BC's native Page Scripting (record/replay `.yml`) plus the
`e2e-replay` harness. This is the layer that catches UI regressions the AL
TestPage suite is structurally blind to, and unlike an ad-hoc agent run it is
recorded once and replayed on demand.

## The three-layer test model

Every flow under test belongs to exactly one layer. Put it in the cheapest layer
that can actually verify it.

1. **AL TestPage suite** (owns: logic, state transitions, validation errors,
   action enable/disable gates, proportional math, FlowField values, permission
   RIMD). Fast, deterministic, runs in a container / CI. Generated by
   `al-userguide-test-writer`, run by `al-test-runner`, coverage checked by
   `al-test-coverage-validator`. This is the default; reach for it first.

2. **Page Scripting `.yml`** (owns: the rendered-UI residue AL TestPage cannot
   observe). Recorded once against a live web client, replayed headless via the
   `e2e-replay` harness. This skill governs this layer.

3. **Manual checklist** (owns: the irreducible. Mobile / phone viewport,
   subjective "does it look right", anything no harness can assert). Smallest
   possible. A one-page pre-release smoke.

### What goes in Page Scripting (and not in an AL test)

AL TestPage runs headless against the platform; it never renders. So only the
things that need a *rendered client* belong in layer 2:

- **Notification toasts** firing (`Notification.Send` is silent in TestPage).
- **Cue / tile rendering and Style** (e.g. an Attention tile turning red when a
  count crosses zero).
- **Page visibility / editability refresh** after a field change (the classic
  "field did not refresh until I tabbed off" class of bug).
- **FactBox refresh** on row change.
- **Dropdown / lookup population and filter-as-you-type narrowing.**
- **Modal / dialog flow** a user actually clicks through (Confirm, StandardDialog).
- **Real posting through the standard codeunits** driven from the UI, where the
  AL test would need a full posting fixture and you want the on-screen outcome.

If a check can be made by reading a record or asserting a field after invoking a
codeunit, it belongs in layer 1. Do not record it.

## Workflow

```
1. bc-extension-test-guide       -> DOCS/TEST_GUIDE.md (all categories)
2. al-userguide-test-writer      -> AL TestPage suite (layer 1)
   + al-test-runner / -coverage-validator
3. THIS skill                    -> for the categories layer 1 cannot reach:
                                    a Page Scripting recording plan + harness
4. e2e-replay/run.ps1 (task)     -> replay the whole set, pass/fail report
```

### Step 1: identify the residue

Read `DOCS/TEST_GUIDE.md` and the green AL suite. For each TEST_GUIDE category
or USER_GUIDE flow, ask: "can an AL TestPage verify this?" Anything in the "needs
a rendered client" list above is residue. List it. Everything else stays layer 1.

### Step 2: write the recording plan

Produce `Page Scripting/E2E-PLAN.md`: a numbered chain of small recordings, one
flow each. For every recording capture:

- **File name** `E2E-NN <flow>.yml` (the `NN` prefix sorts the folder into play
  order; a batch glob runs the chain start to finish).
- **The exact click-path** the human will follow while recording (Tell Me ->
  page -> field -> value -> action), written tight enough to record without
  improvising.
- **The deterministic precondition** (see Step 3).
- **What it verifies** (the residue item from Step 1).

Keep recordings small and single-purpose. One flow per file replays and
maintains far better than one long session.

### Step 3: make it deterministic (the seed)

A recording that depends on ambient data (whatever row happens to be first, a No.
auto-assigned from the live series) is not repeatable. Anchor every recording to
seeded, deterministically-named fixtures:

- A **Test Seed Factory** codeunit (gated behind an `Allow Test Data Seed` toggle,
  DEV/UAT only) that `Clear`s then `Seed`s a known set with a fixed prefix
  (e.g. `FE2E-`). Idempotent: seed inserts what is missing, clear removes the
  prefix.
- For recordings that **create** records, repoint the relevant No. Series at a
  freshly-reset test series during seed, so a recorded "New" always yields the
  same No. (e.g. `FE2E-MOV-001`). Restore the default series on clear. Without
  this, run 2 creates `-002` and the recording's assertions drift.
- Make `E2E-00 Clear and Seed.yml` (just invokes the two Setup actions, asserts
  their confirmation messages) the head of every batch.
- In a lookup, type the full code as a **filter-as-you-type** value so the picker
  narrows to exactly one row before selecting. Never rely on "click the first
  row".

### Step 4: record

The human records in the web client (Settings -> Page scripting (Preview) ->
Start new -> drive the flow -> Stop -> Save). Then tidy each raw `.yml`: a real
name + description, the replay prerequisite, and intent-readable step
descriptions. Keep the recorder's `telemetryId` / `runtimeId` / targeting exactly
as captured (the replay engine correlates on them). Save into `Page Scripting/`.

### Step 5: replay (repeatable)

Use the `e2e-replay` harness (scaffolded into the `bc-extension` template):

```powershell
$env:BC_USER = "you@example.com"; $env:BC_PW = "<password>"
pwsh ./e2e-replay/run.ps1                       # all E2E-*, headed
```

or the **"E2E: Replay Page Scripting recordings"** VS Code task. The harness
batch-replays every recording in order and reports pass/fail. Adding recording
`#N+1` is just dropping a file in `Page Scripting/`.

## Gotchas (already solved in the harness, stated so you do not relearn them)

- **bc-replay cannot run from a path with a space.** Its internal
  `npx playwright test "<spec>"` splits a spaced `node_modules` path and reports
  "No tests found". `run.ps1` installs into a space-free dir and junctions the
  recordings in. Do not try to run it directly from a repo under `...\AL Repos\...`.
- **No interactive-login mode.** Credentials come from env vars (AAD). Push MFA
  works only headed-with-manual-approve (the player waits through the tap).
  Unattended / CI needs a TOTP or password-only account.
- **The recordings globber rejects `..`.** Keep recordings reachable without a
  parent traversal (the harness uses a `recordings` junction); the default
  pattern is `**/recordings/*.yml`.

## When not to use

- The check can be made by reading a record / asserting a field: use an AL
  TestPage (`al-userguide-test-writer`).
- You want a one-off exploratory drive of the UI, no durable artifact: use the
  `bc-webclient-runner` agent instead.
- The check is subjective or mobile-only: leave it in the manual checklist.
